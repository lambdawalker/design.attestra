# Flujos y recuperación de fallos

Comienza en [onboarding](../../../auth/onboarding/README.md). La [confirmación de correo](../../../auth/onboarding/email-confirmation/flow.md) acepta A+B para confirmar automáticamente al abrir el enlace, A+C para ingresar el código directamente en el cliente que inició el registro, o B+C al abrir el enlace en otro cliente. El campo de código aparece desde la pantalla de espera y requiere envío explícito. Leer un enlace no confirma una cuenta. Aceptar signup no prueba entrega. Reenviar invalida material anterior según presupuestos del servidor. Si se pierde una confirmación exitosa, recupera mediante login, no reproduciendo la prueba.

[Crear passkey](../../../auth/onboarding/passkey-creation/flow.md) exige sesión autenticada. La plataforma controla selector y clave privada. Cancelar o usar un dispositivo incompatible conserva el acceso por correo. [Login](../../../auth/login/architecture.md) y [reanudar](../../../auth/onboarding/resume.md) son distintos de la confirmación inicial.

[Captura](../../../auth/onboarding/id-capture/flow.md) sube fotos a S3 privado y fija versiones exactas para comprobar los archivos. En Android, el frente en escala de grises puede iniciar OCR antes de capturar el reverso si el backend anuncia soporte para el par combinado. El par combinado en color se carga como evidencia mientras continúa abierta la revisión de fotos. Al confirmar se abre el resultado correspondiente o se muestra la espera. Repetir una foto invalida el trabajo anterior y prepara un par nuevo dentro de la misma captura. El cliente comprueba el ID de captura y la revisión de imagen antes de mostrar el resultado.

[Extracción y revisión](../../../auth/onboarding/id-parsing/flow.md) usa la extracción guardada en el registro de captura. Si está pendiente, se muestra la espera. Si falla, se abre la entrada manual. Cuando el servidor confirma exactamente los datos y el país de origen enviados, se regresa automáticamente al flujo de la cuenta. Review ID details abre directamente el formulario guardado; no se requiere otro paso Done después de guardar.

[Validación de ID](../../../verification/id-validation/architecture.md) sigue siendo independiente y diferida. “Detalles guardados”, “captura lista” o un destino de éxito de onboarding nunca significan identidad aprobada. Después de que el servidor confirme que el onboarding terminó, la aplicación consumidora puede recibir un callback específico de éxito; cancelar, volver atrás o diferir siguen siendo rutas separadas. [Verificación de domicilio](../../../verification/address/architecture.md) tiene decisiones propias de política/proveedor.

Integración: [API backend](https://raw.githubusercontent.com/lambdawalker/go.appexfission.aws.card-capture/main/docs/agents/index.md), [captura Android](https://raw.githubusercontent.com/lambdawalker/android.apexfission.auth/main/docs/identity-capture.md) y [contrato HTTP cliente](https://raw.githubusercontent.com/lambdawalker/android.apexfission.auth/main/docs/identity/http-contract.md). Sus revisiones son independientes; consulta el registro de evidencia antes de afirmar compatibilidad.

El worker de captura implementa la [extracción asíncrona y la revisión](../../../auth/onboarding/id-parsing/flow.md). Un fallo de extracción permite ingresar datos manualmente. El diagrama describe el diseño del sistema; la API en uso expone la extracción dentro del registro de captura. Para diagnosticar una ejecución, compara la espera observada en Android con la invocación correspondiente del backend.

Después de aceptar la explicación de captura y comprobar la política vigente, el flujo Android solicita el permiso nativo sin otra explicación de la aplicación. Si se rechaza, conserva reintento, cancelación y recuperación en Ajustes. La cámara independiente mantiene su explicación inicial. Restaurar procesamiento o abrir datos guardados no solicita acceso a la cámara.
