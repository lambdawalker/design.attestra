# Email confirmation AWS strategy

**Baseline:** [go.onboarding/infra](https://github.com/lambdawalker/go.onboarding/tree/feat/aws-onboarding/infra) already provisions a Cognito user pool/client, verified SES sender, Custom Message Lambda, Go API Lambda, and HTTP API. Its current `/signup`, `/resend`, and `/confirm` accept email/Cognito code. The A+B/B+C flow below is **new infrastructure and backend work**, not a deployed capability.

1. **Transaction store:** Add an application-owned DynamoDB table keyed by request ID, with the bound email, A challenge, B digest, keyed C digest, generation, explicit expiry, state, and attempt counters. Use conditional writes or transactions to claim a valid proof and rotate B/C atomically. Keep the account-level retry budget independent of a single generation. DynamoDB TTL is cleanup only; the API must enforce expiry itself.
2. **API Lambda:** Change signup, resend, and confirmation contracts as described in [architecture](architecture.md). Require B plus one valid proof before Cognito confirmation or any session issuance. Return a generic signup/resend response for eligible and ineligible addresses, and stable recovery errors. Make concurrent submissions and partially completed provider calls idempotent.
3. **Email delivery:** Use the verified SES sender already configured. Design a message containing one HTTPS link with B/request ID and a separately displayed C; do not put C in the URL or return B/C in API responses. Decide whether the existing Cognito Custom Message trigger can safely compose the revised application message or whether an application-controlled SES send is required. Do not assume the current trigger implements the new protocol.
4. **Session integration:** Prove a server-controlled Cognito confirmation and authenticated-session bridge for both proof paths in a nonproduction stack before replacing the old endpoint. Preserve email OTP recovery if confirmation succeeds but session exchange does not. Remove any publicly reachable `{email, code}` path that bypasses the bound transaction.
5. **Operations:** Give each Lambda only its required Cognito, SES, DynamoDB, and keyed-digest-secret permissions. Protect the digest key with an AWS-managed secret service/KMS-backed storage choice. Redact B, C, full verification URLs, email contents, and tokens from logs. Monitor throttling, delivery failures, expiry, conditional-write conflicts, and sign-in recovery without logging proofs.

Deploy through the existing Pulumi Go stack in stages: table and scoped IAM, revised API/message implementation, then web/native HTTPS link association and an end-to-end test across devices. Confirm the SES identity and production sending readiness before public signup.

AWS references: [DynamoDB transactions](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html), [TTL behavior](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html), [SES verified identities](https://docs.aws.amazon.com/ses/latest/dg/verify-addresses-and-domains.html), and [Cognito email configuration](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-email.html).
