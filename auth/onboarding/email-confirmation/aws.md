# Email confirmation AWS strategy

**Implementation:** [go.apexfission.aws.verifyemail](https://github.com/lambdawalker/go.apexfission.aws.verifyemail) owns proof validation, the SES sender and its optional [native infrastructure module](https://github.com/lambdawalker/go.apexfission.aws.verifyemail/tree/main/infrastructure). [go.apexfission.aws.auth](https://github.com/lambdawalker/go.apexfission.aws.auth) supplies Cognito enrollment/session contracts. [go.attestra.aws](https://github.com/lambdawalker/go.attestra.aws) composes them and owns environment deployment and sender/domain setup. Executable instructions remain in those repositories. The proof table and authentication grant table are distinct resources; confirmation has bounded grant-write access, not ownership of authentication state.

1. **Transaction store:** The Pulumi stack provisions DynamoDB for pending proofs, conditional state transitions, hourly email/source budgets, and single-use session grants. Each transaction binds request ID, email, A challenge, B hash, keyed C digest, generation, expiry, and attempt counters. TTL cleans up later; the API checks expiration before claims.
2. **API Lambdas:** Separate signup, resend, and confirm Lambdas handle `POST /signup`, `POST /resend`, and `POST /confirm`. Signup gives a generic request ID, resend rotates B/C without changing A, and confirm accepts exactly one of A+B, A+C, or B+C. The accompanying high-entropy A or B must validate before code-attempt accounting. Only the winner of the conditional claim can create a Cognito user or request tokens. Manual C allows five wrong attempts per generation and an account budget across resends. A failed downstream session exchange routes to email OTP recovery, not confirmation replay.
3. **Email:** An application-controlled SES send contains an HTTPS link with B/request ID and separately displayed C. A and C do not appear in the URL or API response. The Pulumi stack provisions a SES domain identity and DKIM tokens; publish DNS records, verify the identity, and complete SES sending readiness before deployment to real users.
4. **Cognito session:** The API creates a passwordless, email-verified account only after application proof validation, with invitation email suppressed. Cognito's custom-challenge triggers verify a short-lived single-use server grant before issuing access/ID/refresh tokens. Public Cognito signup is disabled; existing confirmed accounts do not gain a signup shortcut. Check the complete handoff against an actual Cognito user pool and verify that a failed grant cannot issue tokens.
5. **Operations:** Scope API and trigger roles to their table and Cognito pool. Allow signup and resend to send through SES identities in the account and region, with `ses:FromAddress` restricted to the configured sender; the confirm role does not send email. Supply the keyed digest secret through encrypted Pulumi configuration and a pinned Secrets Manager version. Lambda environments carry the ARN/version references, not the raw key. Rotation requires a coordinated rollout that preserves pending proofs. Redact B, C, full verification URLs, tokens, and email content in logs. Monitor delivery failures, exhausted attempts, conditional conflicts, expired transactions, and recovery.

SES verifies the sending identity in the deployment region. In the sandbox it also requires recipient verification. Signup and resend IAM permissions account for SES checking the recipient identity, while `ses:FromAddress` limits which address these functions can use. SES acceptance does not establish inbox delivery, and a generic signup response does not establish SES acceptance. The [Go operations guide](https://github.com/lambdawalker/go.apexfission.aws.verifyemail/blob/main/README.md) owns the exact checks, IAM gotcha, CloudWatch log names, and recovery commands.

The `GET /verify-email` screen is hosted by the client application, never by this API, and has no server-side confirmation side effect. Android implementation and configuration are owned by [android.apexfission.auth](https://github.com/lambdawalker/android.apexfission.auth); the future iOS implementation will document its own universal link and application setup.

AWS references: [DynamoDB conditional writes](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html), [SES verified identities](https://docs.aws.amazon.com/ses/latest/dg/verify-addresses-and-domains.html), [admin-created passwordless users](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AdminCreateUser.html), and [Cognito custom authentication](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-lambda-challenge.html).
