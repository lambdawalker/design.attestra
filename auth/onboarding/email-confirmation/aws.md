# Email confirmation AWS strategy

**Implementation:** [go.attestra.aws.auth](https://github.com/lambdawalker/go.attestra.aws.auth) contains the Go Lambda handlers and [Pulumi stack](https://github.com/lambdawalker/go.attestra.aws.auth/tree/main/infra) for this subfeature. Deployment, SES verification, client link routing, and a live Cognito integration check remain operational steps.

1. **Transaction store:** The Pulumi stack provisions DynamoDB for pending proofs, conditional state transitions, hourly email/source budgets, and single-use session grants. Each transaction binds request ID, email, A challenge, B hash, keyed C digest, generation, expiry, and attempt counters. TTL cleans up later; the API checks expiration before claims.
2. **API Lambdas:** Separate signup, resend, and confirm Lambdas handle `POST /signup`, `POST /resend`, and `POST /confirm`. Signup gives a generic request ID, resend rotates B/C without changing A, and confirm requires B plus exactly one valid A or C. Only the winner of the conditional claim can create a Cognito user or request tokens. Manual C allows five wrong attempts per generation and an account budget across resends. A failed downstream session exchange routes to email OTP recovery, not confirmation replay.
3. **Email:** An application-controlled SES send contains an HTTPS link with B/request ID and separately displayed C. A and C do not appear in the URL or API response. The Pulumi stack provisions a SES domain identity and DKIM tokens; publish DNS records, verify the identity, and complete SES sending readiness before deployment to real users.
4. **Cognito session:** The API creates a passwordless, email-verified account only after application proof validation, with invitation email suppressed. Cognito's custom-challenge triggers verify a short-lived single-use server grant before issuing access/ID/refresh tokens. Public Cognito signup is disabled; existing confirmed accounts do not gain a signup shortcut. Check the complete handoff against an actual Cognito user pool and verify that a failed grant cannot issue tokens.
5. **Operations:** Scope API and trigger roles to their table and Cognito pool. Allow signup and resend to send through SES identities in the account and region, with `ses:FromAddress` restricted to the configured sender; the confirm role does not send email. Keep the keyed digest secret in encrypted Pulumi configuration and limit access to Lambda environment variables. Redact B, C, full verification URLs, tokens, and email content in logs. Monitor delivery failures, exhausted attempts, conditional conflicts, expired transactions, and recovery.

## SES setup for email delivery

1. Set `aws:region` to the region where SES and the Lambdas run (currently `us-east-2`). Set `senderDomain` to `info.attestrabond.com` and `senderAddress` to `verify@info.attestrabond.com` in the Go project's Pulumi stack. Configure `appOrigin` for the verification link and the secret `proofKey` as described in the [Go README](https://github.com/lambdawalker/go.attestra.aws.auth/blob/main/README.md).
2. In Cloudflare DNS for `attestrabond.com`, publish the SES domain verification TXT record and three Easy DKIM CNAME records. Obtain the TXT name/value from `pulumi stack output sesVerificationRecord` and the DKIM token names from `pulumi stack output sesDkimTokens` (or find the same records under **SES → Verified identities → info.attestrabond.com → Authentication**). For each token, add `<token>._domainkey.info.attestrabond.com` as a CNAME to `<token>.dkim.amazonses.com`. Use DNS only, without Cloudflare proxying. Cloudflare may append the zone suffix to record names; check the displayed full hostname before saving. Leave `route53ZoneId` unset when Cloudflare owns DNS; it is only for automatic record creation in a Route 53 hosted zone.
3. Wait until SES reports `VerifiedForSending: true` and `DKIM: SUCCESS` for the sender identity **in the deployment region**. You can inspect these with `./debug/check-ses-identity.ps1` in the Go repo or with `aws sesv2 get-email-identity --profile attestra --region us-east-2 --email-identity info.attestrabond.com`.
4. While `ProductionAccessEnabled` is `false`, SES also requires the **recipient** to be a verified identity in that region. For testing `asd@isdavid.com`, verify the exact email address via the SES verification email, or add `isdavid.com` as another SES domain identity and publish its verification/DKIM DNS records with that domain's DNS provider. Checking the sender domain alone cannot establish recipient eligibility. To email unverified recipients, request SES production access in `us-east-2`. Check status with `./debug/check-ses-account.ps1` in the Go repo.
5. Deploy the updated IAM roles with `pulumi up`. During a sandbox send, SES can authorize against the recipient identity as well as the sender. The signup and resend policies therefore allow `ses:SendEmail` on `arn:aws:ses:<region>:<account>:identity/*`, while `ses:FromAddress` permits only `senderAddress`. Restricting the resource to the sender identity alone caused `AccessDeniedException` for the recipient domain. The SES sandbox verification rule still applies independently of IAM.
6. Submit a fresh signup and inspect the `email-signup` CloudWatch log group if delivery fails. A generic `202` and `request_id` only acknowledge the request; the log's `operation_failed stage=ses_send provider_code=...` identifies SES failures. Keep email addresses, verification links, and proof tokens out of logs. The Go repo's [debug scripts](https://github.com/lambdawalker/go.attestra.aws.auth/tree/main/debug) expose account and identity readiness without changing resources.

Run `go test ./...`, `go vet ./...`, and the Pulumi stack build as described in the [repository README](https://github.com/lambdawalker/go.attestra.aws.auth/blob/main/README.md). The `GET /verify-email` screen is hosted by the client application, never by this API, and has no server-side confirmation side effect.

AWS references: [DynamoDB conditional writes](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html), [SES verified identities](https://docs.aws.amazon.com/ses/latest/dg/verify-addresses-and-domains.html), [admin-created passwordless users](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AdminCreateUser.html), and [Cognito custom authentication](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-lambda-challenge.html).
