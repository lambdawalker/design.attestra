# ID capture AWS strategy

**Baseline:** The [new auth Pulumi stack](https://github.com/lambdawalker/go.attestra.aws.auth/tree/main/infra) does not provision an identity evidence pipeline. The following components are proposed and depend on the selected capture plugin, external provider, consent, retention, and result policy.

1. **Private evidence:** Provision a private S3 bucket with public access blocked and encryption at rest; decide whether a customer managed KMS key is required. An authenticated API issues short-lived, narrowly scoped upload instructions for unique account/submission/evidence-version object keys. Validate actual file type, size, checksum, and expected asset count before accepting a submission. Keep image reads server-side and avoid public object URLs; a presigned PUT to an existing key can overwrite it, so use unique immutable keys and enforce the submission state.
2. **Application state:** Add a verification store, for example DynamoDB, keyed to Cognito `sub` and evidence version. Record submission idempotency key, object references, extracted and corrected fields, `autoReport` and `thirdParty` statuses, timestamps, and the policy decision separately. Use conditional updates to prevent an old callback or worker retry from rewriting a newer result.
3. **Processing and provider:** Finalize an uploaded submission through an authenticated API, validate all assets, and enqueue an asynchronous worker to extract/report. Integrate the selected external provider behind a dedicated adapter and authenticated callback endpoint. If the provider requires long waits, Step Functions callback tasks are one possible orchestrator; an event-driven worker and state store may suffice. Authenticate callbacks, deduplicate event IDs, verify version binding, and keep transient errors retriable.
4. **Access and lifecycle:** Give upload, processing, callback, and status paths separate least-privilege S3, KMS, and table permissions. Define consent, data-region, encryption, retention, deletion, and support-access rules before production; wire lifecycle/deletion jobs to that approved policy. Log request IDs and coarse states, never document images, OCR output, personal fields, provider secrets, or presigned URLs. Monitor queue failures, stuck pending decisions, provider errors, and deletion completion.
5. **Rollout:** Add infrastructure to Pulumi, implement the authenticated submission/status APIs, test retries and version races using a stub provider, then integrate the chosen plugin/provider and verify privacy controls in a nonproduction account. Only surface success after the authoritative policy accepts the completed decision.

AWS references: [S3 presigned uploads](https://docs.aws.amazon.com/AmazonS3/latest/userguide/PresignedUrlUploadObject.html), [DynamoDB conditional writes](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html), and [Step Functions callback tasks](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html#connect-wait-token).
